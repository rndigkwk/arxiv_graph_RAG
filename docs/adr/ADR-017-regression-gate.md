# ADR-017: 품질 회귀는 CI가 기준선과 대조해 막는다

- **상태:** 채택
- **날짜:** 2026-10-16

## 맥락

지금 CI는 lint·test·compile·문서 링크만 봅니다. **답변 품질은 사람이 눌러서 재야** 했고, 그래서
프롬프트를 고치다 두 번 회귀를 냈습니다 — 심판 정확도 21/21 → 11/21, 집계 순위 규칙 한 문장.
둘 다 고친 뒤에 재서 알았습니다.

## 결정

평가를 CI에 넣고 **기준선과 대조해 판정**합니다. 규칙은 다섯 개이고
[`evals/gate.py`](../../evals/gate.py)가 적용하며 판정은 pytest가 합니다.

| 규칙 | 내용 |
|---|---|
| `cases` | 기준선과 이번 평가의 사례 집합이 같은가 |
| `scoring_error` | 채점 함수가 예외로 죽은 건이 없는가 (0) |
| `floor` | 지표가 절대 하한 이상인가 |
| `drop` | 기준선 대비 하락이 허용폭 이하인가 |
| `stable_case` | 기준선에서 만점이던 사례가 이번에 깨졌는가 |

## 교안과 다르게 한 것

### 1. 에이전트 실패와 채점 오류를 구별합니다

교안은 "채점 오류 0" 하나만 둡니다. 그런데 이 프로젝트는 **에이전트 실패율을 5.6~8.3%로
측정했습니다** — `coauthor-03`이 12회 중 1회, `topcited`가 18회 중 1회(`EXPERIMENTS.md` 10절).
실패를 0으로 두면 게이트가 변동으로 터지고, **터지는 게이트는 꺼집니다.**

그래서 채점 오류만 0이고, 에이전트 실패는 상한을 둔 지표(`answer_failure_rate`)로 다룹니다.

### 2. 하한을 이번 측정값에 붙이지 않습니다

[ADR-004](ADR-004-quality-gate-thresholds.md)와 같은 규칙입니다. 근거는 둘입니다.

- 측정된 실패율 5.6~8.3%
- 30건에서 **한 사례가 변동으로 뒤집히면 지표가 1/30 = 0.0333 움직인다**

그래서 허용폭 0.05는 한 사례의 변동을 통과시키고 두 사례를 막습니다. 하한은 두 사례까지
허용하고 세 사례에서 막습니다. `hit_at_k`의 하한이 0.60인 것도 측정값이 아니라 **구조** 때문
입니다 — `author`·`topcited` 12건은 벡터도 PPR도 못 풀고 Text2Cypher가 답하므로(ADR-008) 이
지표가 1.0이 되는 일은 없습니다.

### 3. 게이트 자체를 테스트합니다

[`tests/fixtures/eval_gate/`](../../tests/fixtures/eval_gate)에 가짜 기준선·결과 쌍 7개를 두고
규칙마다 **제대로 실패하는지** 확인합니다. 통과만 시키는 게이트는 게이트가 아니므로, 이 층이
없으면 "통과"가 아무것도 뜻하지 않습니다. 반대로 **하나는 반드시 통과해야** 합니다 — 아무것도
통과시키지 못하는 게이트는 배포를 영구히 막습니다.

실제로 과거 보고서로 검증했습니다. 수정 전 실행은 하한 여섯 개 전부에 걸리고, 중간 실행은
`answer_evidence_precision` 하한과 `topcited-04`·`topcited-06`의 사례별 회귀에 걸립니다 —
그 두 건이 바로 집계 순위 회귀가 있던 구간입니다.

### 4. 결과 파일이 없으면 CI에서는 실패입니다

로컬 `pytest`는 평가를 돌리지 않으므로 건너뜁니다. CI는 `EVAL_GATE_REQUIRED=1`을 켜서 **건너
뛰기가 아니라 실패**가 되게 합니다. 그러지 않으면 평가 단계가 깨진 날 게이트가 초록색이 됩니다.

### 5. 지연과 토큰은 게이트에서 제외합니다

품질이 아니고 실행 환경에 따라 흔들립니다. 게이트가 보면 매번 터집니다. 보고서에는 남습니다.

## 분할

PR은 **가족마다 한 건씩 5건**(smoke), 주간 cron은 30건 전부(full)입니다. 앞에서 5건을 자르지
않는 이유는 이 과제에서 **질문 가족이 승자를 정하기** 때문입니다(ADR-008) — 앞에서 자르면 한
가족만 봅니다. `evals/run.py`에 `--case-ids`를 더해 가족별로 고를 수 있게 했습니다.

## 대가

| 항목 | 값 |
|---|---|
| 토큰 | full 30건 약 366k. 주 1회 |
| PR | smoke 5건이라 한 자릿수 만 토큰 |
| 선행 조건 | Aura가 깨어 있어야 합니다. 평가 전에 `keep_awake.py`를 돌립니다 |

`CLIENT_ID`/`CLIENT_SECRET`은 **인스턴스를 삭제할 수도 있는** 관리 API 자격증명이라 저장소
비밀에 넣지 않았습니다. 그래서 이 워크플로는 멈춘 인스턴스를 깨우지 못하고 **분명하게
실패합니다.** 조용히 통과하는 것보다 낫습니다.

## 남긴 것

**기준선이 1회 실행분입니다.** 교안은 같은 설정으로 세 번 돌려 흔들림을 재고 그 값으로 허용폭을
정합니다. 지금 허용폭은 "한 사례 = 0.0333"이라는 **산술**에서 왔고, 전체 세트의 반복 측정에서
온 것이 아닙니다. 주간 cron이 쌓이면 `--report`를 여러 개 주어 `observed_spread`를 측정값으로
채우고 허용폭을 다시 정합니다.

## 민감도

**사례 수가 바뀌면 허용폭의 근거가 바뀝니다.** 30건에서 한 사례는 0.0333이지만 60건이면
0.0167입니다. 사례를 늘리면 허용폭을 좁혀야 하고, 그러지 않으면 게이트가 느슨해집니다.

## 재현

```bash
uv run python -m evals.run --mode compare --cases evals/cases_graph.json \
  --case-ids author-01,citing-01,coauthor-01,reference-01,topcited-01 \
  --output reports/regression_smoke.json
uv run python -m evals.gate --report reports/regression_smoke.json --split smoke
uv run python -m pytest tests/test_eval_gate.py
```

워크플로는 [`.github/workflows/regression-eval.yml`](../../.github/workflows/regression-eval.yml)입니다.

# ADR-073: 모델이 실패하면 무엇을 할지 말한다 — 제한 시간은 저장된 180회에서 정한다

- **상태:** 채택
- **날짜:** 2026-10-26

## 맥락

모델 호출이 실패하면 화면은 늘 같은 한 줄이었습니다 — "검색 에러: RateLimitError. 연결 상태를
확인하고 다시 질문하세요." **검색은 멀쩡하고, 연결을 확인해도 풀리지 않습니다.**

- 사용 한도가 다 됐으면 초기화를 기다려야 합니다.
- 제공자가 응답하지 않거나 속도 제한에 걸렸으면 잠시 뒤 다시 물으면 됩니다.
- 둘 다 아니면(DB·코드) 지금의 일반 안내가 맞습니다.

같은 저자의 dograg가 2026-10-19에 평가와 운영이 같은 키를 쓰다 한도를 다 썼고, 그 뒤 모든 질문이
같은 한 줄로 끝났습니다. 그쪽 `src/model_outage.py`를 가져옵니다.

그리고 기다림이 길었습니다. 답변 모델은 `timeout=120`에 라이브러리 기본 재시도 2번이라, 제공자가
멈추면 한 호출이 **최악 6분**을 붙잡았습니다. 이 값은 잰 적이 없는 값이었습니다.

## 결정 1 — 실패를 셋으로 가르고, 할 수 있는 것을 함께 말합니다

`src/model_outage.py`가 예외 사슬(`__cause__`·`__context__`)을 따라가며 가릅니다.

| 예외 | 분류 | 안내 |
|---|---|---|
| `RateLimitError`, 코드 `insufficient_quota` | `quota` | 한도가 초기화되면 다시 시도 |
| 그 밖의 `RateLimitError`, `APIConnectionError`(시간 초과 포함), `InternalServerError` | `unavailable` | 잠시 뒤 다시 시도 |
| 그 밖(Neo4j·코드 오류) | `None` | 지금의 일반 안내 그대로 |

두 안내 모두 끝에 "홈·PageRank 순위·품질 게이트 탭은 모델 없이 동작합니다."를 붙입니다.

같은 429라도 속도 제한과 한도 소진은 할 일이 다르므로 본문 코드로 가릅니다. **DB 오류를 모델
장애로 적지 않는 것**이 반대편 실수이므로 Neo4j `ServiceUnavailable`을 시험의 대조군으로 둡니다.

화면에서 모델을 부르는 자리 넷(답변, 번역 버튼, 저장 논문 비교, 답변별 비교)이 모두 이 분류를
거칩니다. 하나라도 빠지면 그 자리만 옛 안내가 되므로 시험이 자리 수를 셉니다.

## 결정 2 — 제한 시간 60초, 재시도 1번

저장된 회귀 실행 180회(`reports/baseline_*_run?.json`, 6개 리포트 × 30문항)에서 잽니다.

| 측정 | 최대 |
|---|---|
| 조건 판정 노드 한 번 | 9.6초 |
| `generate` 노드 한 번 전체(모델 호출 여럿과 도구 포함) | 36.3초 |
| 질문 하나 전체 | 42.5초 |

한 모델 호출은 `generate` 노드 한 번보다 길 수 없으므로 **60초는 측정된 어느 호출도 끊지
않습니다.** 재시도를 1번으로 줄여 최악이 6분에서 2분으로 줄어듭니다. 시험이 저장된 실행에서
최대를 다시 계산해 제한 시간과 비교하므로, 느린 실행이 쌓이면 시험이 먼저 알립니다.

번역 모델과 임베딩은 이미 60초였고 재시도만 1번으로 맞췄습니다.

## 민감도

- ~~**번역 지연은 잰 적이 없습니다.**~~ **같은 날 쟀습니다**(EXPERIMENTS 11-52). 번역 도구 10회의
  최대가 <!--n:reports/inside_generate.json#tools.translate_to_english.max-->2.8<!--/n-->초로 60초의
  20분의 1 아래입니다. 앱의 번역 버튼(한국어로)은 같은 클라이언트를 쓰지만 답변 전체를 옮기므로
  더 길 수 있고, 그쪽은 여전히 재지 않았습니다.
- **스트리밍 호출의 제한 시간은 전체 시간이 아닙니다.** httpx의 시간 초과는 연결과 각 읽기 사이에
  걸리므로, 답변 모델은 토큰이 계속 오는 한 60초를 넘겨도 끊기지 않습니다. 끊기는 것은 60초 동안
  아무것도 오지 않을 때입니다 — 제공자가 멈춘 경우가 바로 그것입니다.
- **재시도 1번이 일시적 오류를 더 자주 화면에 올릴 수 있습니다.** 180회 중 재시도로 살아난 호출이
  몇 번인지는 리포트에 남지 않아 몰랐습니다. 같은 날부터 평가 보고서가 SDK 재시도를 셉니다 — 첫
  30문항에서 <!--n:reports/inside_generate.json#sdk_retries.total-->0<!--/n-->번이었습니다
  (EXPERIMENTS 11-52). 30건 한 번이라 "재시도가 드물다"까지만 말합니다. 늘어나면 안내는 "잠시 뒤
  다시"이므로 사용자가 할 일은 같습니다.
- **분류는 openai 3.3.0의 예외 계층에 기댑니다**(`APITimeoutError` ⊂ `APIConnectionError`,
  `InternalServerError` ⊂ `APIStatusError`). 계층이 바뀌면 시험이 실패합니다.
- **한도 소진 자체는 막지 않았습니다.** dograg는 평가용 키와 운영용 키를 나누려다 조직 키 정책에
  막혔습니다. 이 저장소도 회귀 평가(CI의 `OPENAI_API_KEY`)와 배포 앱이 같은 키를 쓰는지는
  사용자가 정할 일이라 이 ADR에서 바꾸지 않았습니다.

## 넘지 않은 선

- 분류 결과를 트레이싱으로 보내지 않았습니다. 보내려면 분류 코드만 보내야 하고(ADR-023), 지금은
  화면 안내가 목적입니다.
- 실패한 질문을 자동으로 다시 묻지 않았습니다. 한도 소진에서 다시 묻는 것은 비용만 듭니다.

# ADR-047: 적재가 벡터 인덱스에 안 보이는 논문을 거부한다

- **상태:** 채택
- **날짜:** 2026-10-20

## 맥락

[ADR-045](ADR-045-what-to-delete-before-adding-a-month.md)가 "다음 달 스냅샷은 아무것도 지우지
않고 들어갑니다"로 끝났습니다. **노드와 관계 수에 대해서는 맞습니다.** 그런데 그 다음 달을
실제로 넣는 도구를 보니 한 칸이 비어 있었습니다.

```cypher
MERGE (p:ArxivPaper {arxiv_id: row.arxiv_id})
SET p.title = ..., p.abstract = ..., p.primary_category = ...,
    p.categories = ..., p.pdf_url = ..., p.source = ..., p.oai_datestamp = ...
```

**`embedding`이 없습니다.** 그리고 `pipeline/oai.py`가 돌려주는 레코드에도 그 키가 없습니다 —
OAI-PMH는 메타데이터만 줍니다. 임베딩을 만드는 곳은 파이프라인이 아니라 적재 노트북입니다.

그래서 `pipeline.ingest --load`로 한 달을 넣으면 그 논문들이 이렇게 됩니다.

| 경로 | 새 논문이 나오는가 |
|---|---|
| `search_graph` (저자·인용·공동저자 Cypher) | **예** |
| `search_papers` (벡터 인덱스) | **아니오** |
| 관련 논문 3단계 임베딩 보충(ADR-040) | **아니오** |

**조용한 종류의 손상입니다.** 앱은 돌고, 그래프 질문은 정상이고, 벡터 질문만 그 논문을 못
찾습니다. 어느 질문이 무엇을 놓쳤는지 세지 않으면 드러나지 않습니다.

## 게이트는 있었습니다 — 다만 하류에 있었습니다

`pipeline/quality.py`가 스냅샷 게이트로 **임베딩 커버리지 100%**와 차원 균일을 요구합니다
(ROADMAP 9-4가 "누락 탐지가 목적"이라고 적어 둔 그것입니다). 그러니 영원히 숨지는 않습니다.

문제는 **순서**입니다.

```
적재(Aura에 씀) → ... → 다음 스냅샷 빌드 → 게이트가 잡는다
```

게이트가 걸리는 시점에 데이터는 **이미 Aura에 있습니다.** 그 사이 앱은 반쯤 보이는 그래프를
서비스합니다. 그리고 Aura Free에서 되돌리는 일은 쉽지 않습니다 — 관계가 84.6% 찬 인스턴스에서
지우는 작업은 ADR-045가 "별도 설계"로 남겨 둔 것입니다.

## 결정

**적재 전에 같은 검사를 한 번 더 합니다.** 용량 검사가 "들어갈 자리가 없으면 적재하지
않는다"인 것과 같은 선입니다 — 데이터가 깨끗해도 **쓸 수 없는 모양이면** 적재해서는
안 됩니다.

| 검사 | 막는 것 |
|---|---|
| 보강 실패율 | 인용이 비어 있는 배치 |
| 용량 | 한도를 넘는 배치 |
| **임베딩** | **벡터 검색에 안 보이게 되는 배치** |
| 멱등 적재 | 두 번 넣었을 때의 중복 |

`plan_embeddings()`가 **새 논문만** 셉니다. 이미 그래프에 있는 논문은 `MERGE_PAPER`의 `SET`이
`embedding`을 건드리지 않으므로 다시 적재해도 갖고 있던 것이 남습니다. 차원이 다른 임베딩도
거부합니다 — 1024차원을 768 인덱스에 넣으면 조용히 쓸 수 없는 노드가 됩니다.

**상수를 스냅샷 게이트에서 가져옵니다.** `EMBEDDING_DIMENSIONS`·`MIN_EMBEDDING_COVERAGE`를
`pipeline.quality`에서 임포트합니다. 여기서 다시 적으면 두 검사가 갈라지고, **상류에서 통과한
배치가 하류에서 막힙니다.** 같은 날 `capacity.py`에 한도를 중복으로 적어 3.4개월을 5.1개월로
셌던 것과 같은 함정입니다(ADR-045).

### 넘기는 길은 명시적입니다

`--allow-missing-embeddings`가 필요합니다. 적재 직후 임베딩을 채울 계획이라면 그것이 맞는
작업 순서이고, 그때는 **알고 하는 것**입니다. 기본값으로 통과시키지 않는 이유는 하나입니다 —
모르고 하면 되돌릴 수 없습니다.

`--dry-run`은 막지 않고 **보고합니다.** 적재하지 않으므로 손상이 없고, 무엇이 비었는지는
봐야 합니다.

## ADR-045에 대한 정정은 아닙니다

ADR-045가 센 것은 **자리**이고 그 숫자는 그대로입니다(관계 41,634개, 논문 4,657편, 3.4개월).
이 결정이 더하는 것은 **그 자리를 쓰려면 임베딩 단계가 먼저 필요하다**는 것입니다. 한 달을
넣는 작업의 순서가 이렇게 정해집니다.

1. 수집 (`pipeline.ingest --dry-run`으로 자리와 임베딩 상태 확인)
2. **임베딩 만들기** — 지금은 `notebooks/arxiv_ai_kg_to_aura.ipynb`가 하는 일
3. 적재 (`--load`)
4. 스냅샷 빌드 + 게이트

2번이 없으면 3번이 멈춥니다. 그것이 이 결정의 전부입니다.

## 넘지 않은 선

**임베딩 단계를 파이프라인에 넣지 않았습니다.** 넣는 것이 맞는 방향이지만 그것은 OpenAI
호출을 적재 경로에 들이는 일이고(비용·실패 처리·예산 소진까지 ADR-044와 엮입니다), 지금
필요한 것은 **조용한 손상을 막는 것**입니다. 막는 쪽이 먼저입니다.

**이미 적재된 그래프를 검사하지 않았습니다.** 이 검사는 들어오는 배치만 봅니다. 현재 Aura의
커버리지는 스냅샷 게이트가 보증합니다(2026-10-14 스냅샷이 통과했습니다).

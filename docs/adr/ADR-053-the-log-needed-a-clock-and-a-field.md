# ADR-053: 로그에 필요한 것은 핸들러가 아니라 시각과 필드 하나였다

- **상태:** 채택
- **날짜:** 2026-10-21

## 맥락

로거가 둘 있습니다 — `arxiv_graph_rag.validation`(답변 검증 실패의 사유 코드, ADR-019)과
`arxiv_graph_rag.graph`(그래프 읽기 재시도, ADR-015). **어디에도 핸들러가 없었습니다.**

[ADR-052](ADR-052-the-sixty-seconds-is-not-for-the-steady-state.md)가 이것을 막는 자리로
만났습니다. 그 ADR이 `connection_acquisition_timeout` 하한을 **42초**로 정했는데 근거가
2026-10-15의 **한 번**("90초 뒤 자체 회복")이고, 민감도 절에 이렇게 적었습니다.

> 그 사고가 블랙홀이었다면 60초가 구한 것이고, 거부였다면 재시도는 아무 일도 하지 않았습니다.
> 둘의 성질은 쟀지만 **어느 쪽이었는지는 모릅니다.** 운영 로그가 있으면 답할 수 있는데,
> 지금 `graph_logger`는 예외 **유형**만 남기고 핸들러가 붙어 있지 않습니다.

## 먼저 확인한 것 — 버려지고 있던 것은 아닙니다

핸들러가 없으면 파이썬의 `logging.lastResort`가 WARNING 이상을 stderr로 보냅니다. 그래서
줄은 보였고 Streamlit Cloud 앱 로그에도 남았습니다. **"로그가 없다"가 아니라 "형식이
없다"였습니다.** 이것을 확인하지 않고 "로그가 안 남는다"로 적었으면 틀린 맥락 위에 결정을
세울 뻔했습니다.

| 없던 것 | 그래서 못 하던 것 |
|---|---|
| 시각 | **"언제, 얼마나 자주, 얼마나 오래"를 셀 수 없습니다** |
| 로거 이름 | 검증 실패와 그래프 재시도가 한 줄씩 섞입니다 |
| 수준 손잡이 | 조용히 하거나 더 보게 할 방법이 없습니다 |

## 그런데 핸들러만으로는 ADR-052의 질문에 답하지 못합니다

이것이 이 ADR의 내용입니다. 쟀습니다 — **두 저하 모드가 같은 예외입니다.**

| 실패 모드 | 예외 유형 | 걸린 시간 |
|---|---|---|
| 블랙홀(패킷 버려짐) | `ServiceUnavailable` | **획득 타임아웃을 꽉 채움**(≈60초) |
| 거부(포트 닫힘) | `ServiceUnavailable` | **≈2초** |

`graph_logger`가 남기던 것은 `type(exc).__name__`뿐입니다. 그러니 **시각을 붙여도 두 모드가
구별되지 않습니다** — 같은 글자가 찍힙니다. 구별하는 것은 **경과 시간**입니다.

## 결정

### 1. `arxiv_graph_rag`에만 핸들러를 붙입니다 — 루트는 건드리지 않습니다

[`pipeline/logs.py`](../../pipeline/logs.py)의 `configure()`를 [`app.py`](../../app.py)의
**`main()` 첫 줄**이 부릅니다. `load_chatbot()`보다 앞서야 합니다 — `chatbot`은 임포트 시점에
Aura에 붙으므로 설정이 늦으면 앱이 뜰 때의 줄이 형식 없이 나갑니다.

> **모듈 최상단에 두었다가 옮겼습니다.** 임포트만으로 전역 로깅이 바뀌는 것은 부작용이고,
> `app`을 임포트하는 테스트 두 개(`test_paper_comparison`, `test_saved_papers`)가 실제로 그
> 부작용을 받았습니다. Streamlit은 스크립트를 `__main__`으로 돌리므로 `main()` 안도 진입점이고,
> 거기서는 부작용이 없습니다. 테스트가 최상단에 다시 생기는 것을 막습니다.

- **루트 로거를 설정하지 않습니다.** Streamlit과 neo4j 드라이버의 줄까지 형식이 바뀌고,
  그건 우리가 정할 일이 아닙니다.
- **`propagate = False`.** Streamlit이 루트를 설정하므로 올려보내면 **같은 줄이 두 번**
  찍힙니다.
- **두 번 불러도 우리 핸들러가 늘지 않습니다.** Streamlit은 상호작용마다 스크립트를 다시
  돌립니다 — 막지 않으면 **재실행 수만큼 줄이 복제**됩니다. 핸들러에 표식을 달아 알아봅니다.
- **세는 것은 우리가 붙인 것뿐입니다.** 처음에 전체 개수로 "이미 설정됐나"를 판단했고,
  **그것이 틀렸습니다** — `propagate=False`인 로거를 보면 **pytest가 자기 포착 핸들러를
  직접 붙입니다**(`LogCaptureHandler`, `_FileHandler`, `_LiveLoggingNullHandler`). 전체 테스트
  안에서 `len(handlers) == 1`이 3이 되어 여섯 건이 깨졌고, 단독 실행에서는 통과했습니다.
  호스트가 무엇을 붙이든 그건 우리 일이 아니므로 **표식으로 가립니다.**
- **시각은 UTC입니다.** 두 기계의 줄을 나란히 읽어야 하고 Aura 콘솔도 UTC입니다.
- **`configure()`는 무엇을 했는지 돌려줍니다.** 조용히 설정하고 아무 말도 하지 않으면
  안 붙은 것과 구별되지 않습니다.

### 2. 재시도 로그에 `seconds=`를 더합니다 — 이것이 실제 답입니다

[`chatbot.read_with_retry`](../../src/chatbot.py)가 시도마다 걸린 초를 함께 적습니다. 그 한
필드가 ADR-052의 42초 하한을 **관측 하나가 아니라 분포 위에** 세웁니다. 사고가 다시 나면
`seconds=60.1`인지 `seconds=2.0`인지로 모드가 갈립니다.

### 3. 마지막 시도의 실패도 적습니다

예전에는 세 번째 실패를 그냥 올려보냈습니다. 그래서 **세 번 실패한 사고가 로그에는 두 줄로만**
남았고, 가장 알고 싶은 줄이 빠져 있었습니다. 사유 코드를 `graph_load_retry`와
`graph_load_failed`로 **구분해서** 적습니다 — 섞으면 "재시도 끝에 성공"과 "끝내 실패"를
가를 수 없습니다.

### 4. 담는 것은 메타데이터뿐입니다 — 선은 그대로입니다

질문 문장, 답변 본문, Cypher, 조회한 행을 남기지 않습니다. [ADR-023](ADR-023-what-to-trace.md)
결정 3번이 **추적**에 대해 정한 것과 같은 선을 **로그**에도 적용합니다.

| 남기는 것 | 어디 |
|---|---|
| 요청 id, 시도 번호, 단계, 사유 코드 | `validation` |
| 시도 번호, 예외 유형, **초** | `graph` |

테스트가 이것을 **단어가 아니라 인자로** 검사합니다. `answer_validation_failed`는 이벤트
이름이지 데이터가 아니므로, 서식 문자열에 `answer`가 있다고 막으면 안 됩니다. 그래서 AST로
호출 인자를 꺼내 허용 목록과 맞춥니다 — 데이터를 넘기려면 그 목록을 늘려야 하고, 그러려면
이 ADR을 고쳐야 합니다.

### 5. 수준 오타는 "전부 보기"가 아니라 기본값으로 떨어집니다

`ARXIV_LOG_LEVEL=WARINNG`가 DEBUG로 읽혀 운영 로그를 데이터로 채우면 안 됩니다.
`LANGFUSE_MAX_TRACES`에서 정한 것과 같은 방향입니다(ADR-023) — **쿼터나 데이터를 늘리는
쪽으로 틀리지 않습니다.**

## 결과

- 기본값은 **WARNING → stderr**입니다. 지금과 같은 목적지이고, 줄에 시각·수준·로거 이름이
  붙습니다. Streamlit Cloud에서는 앱 로그에 그대로 들어갑니다.
- `ARXIV_LOG_FILE`을 주면 회전 파일(1MB × 3)이 더해집니다. **못 쓰면 앱을 멈추지 않고**
  사유를 돌려줍니다 — 다만 조용히 묻지도 않습니다.
- **Langfuse와 무관합니다.** 추적은 ADR-023대로 앱에서 꺼져 있고 조직 한도가 11월 6일에
  풀립니다. 이 결정은 그것을 기다리지 않습니다 — 핸들러는 쿼터를 쓰지 않습니다.

## 재현에 쓰는 사본이 하나 갈라졌습니다

[`tests/test_graph_load_retry.py`](../../tests/test_graph_load_retry.py)는 `chatbot`을
임포트할 수 없어(임포트만으로 Aura·OpenAI에 붙습니다) 재시도 규칙을 **순수 함수로 재구성**해
검증합니다. 이번에 실물을 고치면서 그 사본이 갈라졌습니다 — **이 저장소에서 손으로 유지하는
두 벌이 갈라진 일곱 번째 자리**입니다.

사본을 맞추는 것으로 끝내지 않고, **실물 소스를 파싱해 같은 필드가 있는지 확인하는 테스트**를
함께 두었습니다. 사본이 다시 갈라지면 그쪽이 막습니다.

## 민감도

**이 결정은 "다음 사고가 난다"에 기대고 있습니다.** `seconds=`는 저하가 **다시 일어날 때만**
값을 만듭니다. 2026-10-15 이후 한 번도 없었으므로, 분포는 아직 **표본 0**입니다. 42초 하한은
이 ADR로 **답이 나온 것이 아니라 답할 수 있게** 됐을 뿐입니다.

**줄을 모아 읽는 곳이 없습니다.** stderr와 (원하면) 파일까지입니다. Streamlit Cloud의 앱
로그는 손으로 봐야 하고, 재시작하면 사라집니다. "한 달에 몇 번"을 세려면 모으는 곳이
필요하고, 그것은 저장 백엔드 결정이라 여기서 하지 않았습니다.

**앱만 설정합니다.** `configure()`를 부르는 곳은 [`app.py`](../../app.py) 하나입니다.
CLI 경로(`evals`, `scripts`)에서 `chatbot`을 쓰면 그 줄은 여전히 `lastResort`로 나가 시각이
없습니다. 거기서는 사람이 명령을 보고 있으므로 지금은 문제가 아니지만, **주간 크론의 줄에는
시각이 없습니다.** 필요해지면 그때 진입점을 늘립니다 — 모든 모듈에 설정을 뿌리지 않습니다.

**검증 로그 쪽은 초가 없습니다.** `log_validation_failure`에는 지연이 의미가 없다고 보고
넣지 않았습니다. 틀렸다면 — 보류 사유가 시간과 상관이 있다면 — 그때 더합니다.

## 재현

```bash
# 줄의 모양
ARXIV_LOG_LEVEL=INFO uv run streamlit run app.py --server.fileWatcherType none

# 두 저하 모드가 같은 예외라는 것
uv run python -m scripts.measure_connection_acquisition --runs 1 --warm 1
```
